# Plan for closing gaps 023, 024, 043, 049

## Scope

Dieses Dokument beschreibt den Umsetzungsplan fuer die Gaps 023, 024, 043 und 049.
Der Fokus liegt auf Keyboard-first, touch-optimierten Feldworkflows, EDI/API-Hub und Security-Hardening.

Dieses Dokument ist ein Umsetzungsplan und nicht die operative Source-of-Truth fuer den Lieferstatus.

## Gap 023: Keyboard-first fuer alle Kernmasken
**KPI-Ziel:** >=90% Kernflows ohne Maus bedienbar
**Aufwand:** M (2-4 Wochen), Prioritaet: P1, Horizon: H2

### Current State
- Core masks are partially operable via keyboard, but many require mouse for certain actions.
- Need to audit existing keyboard navigation and shortcuts.

### Requirements
- All core masks must be operable via keyboard for >=90% of core flows.
- Logical tab order, visible focus indicators, and keyboard shortcuts for common actions.
- No trapping of keyboard focus.

### Design
- Audit existing masks and identify gaps in keyboard operability.
- Define keyboard navigation standards based on WCAG 2.1 and common desktop application patterns.
- Implement a keyboard navigation service to manage focus and shortcuts centrally.
- Update each mask to adhere to the standards.

### Acceptance Criteria
- Automated and manual tests confirm >=90% of core flows can be completed without mouse.
- All core masks pass keyboard accessibility audit (e.g., using axe-core or similar).
- Documentation of keyboard shortcuts is available and up-to-date.

### Implementation Steps
1. Create an inventory of all core masks and their current keyboard operability.
2. Define keyboard navigation standards and shortcuts.
3. Implement a keyboard navigation service (if not existing).
4. Update each core mask to meet the standards (tab order, focus indicators, shortcuts).
5. Add global keyboard shortcuts for common actions (e.g., save, delete, new).
6. Conduct accessibility testing and fix issues.
7. Update documentation and user training materials.

## Gap 024: Touch-optimierte Feldworkflows (Tablet/Lager/Waage)
**KPI-Ziel:** Fehlbedienungen auf Touch -40%
**Aufwand:** M (2-4 Wochen), Prioritaet: P1, Horizon: H1

### Current State
- Field workflows are primarily designed for desktop mouse interaction.
- Touch targets may be too small, leading to misoperations on touch devices.

### Requirements
- Reduce touch misoperations by 40% in field workflows (tablet, warehouse, scale).
- Ensure touch targets are at least 44x44 dp with sufficient spacing.
- Optimize layout for touch (larger buttons, simplified forms, etc.).

### Design
- Identify field workflows used on touch devices.
- Review current UI for touch target sizes and spacing.
- Apply touch optimization guidelines (e.g., Android/iOS touch guidelines, WCAG 2.1 for touch).
- Adjust UI components and layouts for touch.

### Acceptance Criteria
- Touch misoperations reduced by 40% as measured by user testing or analytics.
- All touch targets meet minimum size and spacing requirements.
- Positive user feedback on touch usability.

### Implementation Steps
1. Identify which field workflows are used on touch devices (tablet, warehouse, scale).
2. Audit current touch target sizes and spacing in these workflows.
3. Define touch optimization standards (min 44px touch targets, 8px spacing).
4. Update UI components and layouts to meet touch standards.
5. Simplify complex forms for touch (e.g., multi-step, large buttons).
6. Test with actual touch devices and gather user feedback.
7. Iterate based on feedback and measurements.
8. Update documentation and guidelines for touch-optimized UI.

## Gap 043: EDI/API Hub fuer Kunden/Lieferanten/Behoerden
**KPI-Ziel:** >=80% Dokumentaustausch digital
**Aufwand:** L (4-8 Wochen), Prioritaet: P1, Horizon: H2

### Current State
- Document exchange with customers/suppliers/authorities is partially digital (e.g., email, manual upload).
- Some EDI/API capabilities exist but are not centralized or comprehensive.

### Requirements
- Centralized hub for EDI (EDIFACT, X12, etc.) and API (REST/JSON) document exchange.
- Support for common business documents (orders, invoices, shipping notices, etc.).
- >=80% of document exchange with external parties occurs via the hub.

### Design
- Analyze current document exchange processes and volumes.
- Design a hub that supports standard EDI formats and/or REST/JSON APIs.
- Implement security (authentication, authorization, encryption) for the hub.
- Integrate with existing backend processes (e.g., order-to-cash, procure-to-pay).
- Provide monitoring and error handling.

### Acceptance Criteria
- Hub is operational and supports required EDI/API formats.
- Integration with at least two key business processes (e.g., order entry, invoice processing).
- Measurement shows >=80% of document exchange with external parties is digital via the hub.
- Hub meets security and reliability requirements.

### Implementation Steps
1. Define the scope of document types and partners for the hub.
2. Choose EDI standards and/or API specifications to support.
3. Design the hub architecture (components, data flows, security).
4. Implement the hub with endpoints for sending/receiving documents.
5. Integrate with backend processes (e.g., trigger on order creation, invoice generation).
6. Implement security measures (OAuth, API keys, encryption, etc.).
7. Set up monitoring, logging, and error handling.
8. Pilot with a few partners and measure digital exchange percentage.
9. Roll out to all partners and optimize.
10. Document the hub and provide partner onboarding materials.

## Gap 049: Security-Hardening (OIDC, RBAC fein, Secrets, Audit)
**KPI-Ziel:** 0 kritische Findings in Pentest
**Aufwand:** L (4-8 Wochen), Prioritaet: P0, Horizon: H1

### Current State
- Some security measures are in place (basic authentication, logging).
- Potential vulnerabilities in authentication, authorization, secrets management, and audit.

### Requirements
- Implement OIDC for authentication.
- Implement fine-grained RBAC (role-based access control).
- Implement secure secrets management (e.g., using a vault or environment variables).
- Enhance audit logging to cover security-relevant events.
- Achieve 0 critical findings in a penetration test.

### Design
- Review current authentication and authorization mechanisms.
- Design OIDC integration (e.g., using an identity provider like Azure AD, Keycloak).
- Design fine-grained RBAC model (roles, permissions, policies).
- Design secrets management (where to store secrets, how to rotate, etc.).
- Design audit logging for security events (login, permission changes, data access, etc.).
- Ensure compliance with relevant standards (e.g., ISO 27001, GDPR if applicable).

### Acceptance Criteria
- Penetration test reports 0 critical findings.
- OIDC is functional and used for authentication.
- RBAC is enforced and limits access based on roles.
- Secrets are not hardcoded and are managed securely.
- Audit logs capture security-relevant events and are tamper-evident.

### Implementation Steps
1. Conduct a preliminary security assessment to identify vulnerabilities.
2. Select and integrate an OIDC provider (if not already present).
3. Implement fine-grained RBAC across the application (backend and frontend).
4. Implement secrets management (e.g., move secrets to environment variables or a vault).
5. Enhance audit logging to include security-relevant events.
6. Implement additional security headers and protections (e.g., CSP, HSTS).
7. Conduct internal security testing and fix issues.
8. Conduct a penetration test and address any findings.
9. Iterate until 0 critical findings are reported.
10. Document the security architecture and procedures.
