# RLS P3: Pilot domain_finance + Buchungsjournal (2026-10-26)

Phase P3, Zweig `claude/rls-p3-pilot-20261026` (gestapelt auf P2, PR #58).

## Aenderung

Migration `rls_pilot_finance_20261026` (nach `inventory_service_shape_20261026`):

- `public.rls_current_tenant()` = `NULLIF(current_setting('app.tenant_id', true), '')`, die
  eine Definition des aktuellen Mandanten fuer alle Policies.
- 22 Tabellen (20 `domain_finance`, `domain_erp.journal_entries`, `journal_entry_lines`):
  `ENABLE ROW LEVEL SECURITY`, Policy `tenant_isolation`:
  `USING (tenant_id = rls_current_tenant() OR (tenant_id = 'system' AND rls_current_tenant() IS NOT NULL))`,
  `WITH CHECK (tenant_id = rls_current_tenant())`. Kein `FORCE` (Eigentuemer = Migrationen).
  Fehlt eine Tabelle (zwei L3-Tabellen gibt es nur frisch), wird sie uebersprungen.
- `journal_entry_lines.tenant_id` (nullbar) wird aus dem Kopf gefuellt (gewachsen: 2 Zeilen).
- `aufbewahrungsfristen`: Platzhalter der Seed-Migration standen unter `SYSTEM` (Grossbuchstaben), jetzt `system` (Fund aus P4; der Code liest nur je Mandant).

Vorpruefung: alle 8 rohen Insert-Wege und beide ORM-Wege fuer Buchungszeilen setzen `tenant_id`;
die Hash-Kette des Journals arbeitet je Mandant, die Kontosperre liest `chart_of_accounts`
(noch ohne RLS).

## Pruefung (valeo_probe, eine Transaktion, ROLLBACK, als valeo_app)

`tests/test_rls_p3_pilot.py` (8): alle Pilottabellen mit RLS und genau einer Policy, ohne
`FORCE`; lesen nur eigener Mandant + `system`; ohne Mandant nichts sichtbar und nichts
schreibbar; Schreiben fuer fremden Mandanten und als `system` scheitert, fuer den eigenen
gelingt; fremde Zeilen aendern/loeschen trifft 0 Zeilen; eigene Zeile nicht zu fremdem
Mandanten verschiebbar; `system`-Zeilen lesbar, nicht aenderbar; Ende zu Ende ueber
`tenant_scope` und den P2-Mechanismus.

Negativprobe: Policy `USING (true)` → 4 Lesetests rot (Schreibschutz bleibt ueber
`WITH CHECK`). Pruefstand danach unveraendert (Revision, 0 RLS-Tabellen).

## Grenzen und Auflagen

- **Bestehende Anwendungstests pruefen RLS nicht:** sie verbinden als Superuser, der RLS
  immer umgeht. Nachweis deshalb ueber die Tests oben als `valeo_app`.
- **Wochen- und Monatsberichte** zaehlen `journal_entries` mandantenuebergreifend; unter RLS
  sehen sie ueber `valeo_app` 0 Buchungen, bis P6 die Systemverbindung liefert.
- **Reihenfolge der Auslieferung:** die Migration darf nur zusammen mit P1+P2 im laufenden
  Backend ankommen. Ohne P2 ist `app.tenant_id` leer und das Backend saehe in den 22 Tabellen
  nichts. Live (valeo_neuro_erp) ist nichts angewendet.
